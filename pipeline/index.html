One file the business runs on

A daily pipeline I designed, built and run for a US consumer debt-relief company. It rebuilds a 254,513-client, 140-column view of the business from a production database, a phone system, text logs, a mobile app and survey reports, and feeds the three Power BI dashboards that customer experience, finance and leadership work from.

  • 28steps, started with one click
  • 15xfaster main query: about 2 hours to about 8 minutes
  • 6source systems joined into one row per client
  • 91%accurate hardship classifier, scoring 99% of clients

Built with PostgreSQL, Python (pandas, scikit-learn, NumPy, PyArrow), Streamlit, SSH tunnelling, RingCentral API, Power Automate, OneDrive and Power BI.

      Three stories behind the dots

      Two hours to eight minutes, with the same answer

      The main query had grown to about two hours. The obvious theory, missing indexes, was wrong. The real cause was stale table statistics: the database planned for about 60,000 clients instead of 226,000 and chose 1.6 million one-at-a-time lookups. With read-only access and no admin rights, I changed how the query reads its biggest tables. The output was proven identical three ways.

      Main query runtime, minutes

      Each bar is a real run. The query kept growing as fields were added, until the fix on 2 October 2026.

      The best time to call was our own office clock

      The pipeline picked each client's "best time to call". A back-test on about 2 million calls showed calling at that time did slightly worse. Six better rules all came out at about zero. The real signal: the dialer's reach collapses in the early afternoon, when it makes the most calls, while manual calls hold steady all day. The recommendation changed from a per-client model to moving dialer volume.

      Reading 252,000 hardship stories

      Clients explain in their own words why they are struggling, but the CRM stores no category. A TF-IDF and logistic-regression model, trained on about 99,000 labelled descriptions, sorts each one into ten categories. 91.3% accurate on held-out data, with a median confidence of 0.96, and the first part of every client's risk segment.

      How it stays right

      Proving every change

      • Ground truth: field-by-field match rates against the original export and the source system's own screens.
      • Drift-controlled checks: compare only clients whose records can no longer change.
      • Determinism: two back-to-back runs must be identical.
      • Plan checks after every SQL edit, and timed runs for anything touching the heaviest tables.
      • Row counts and duplicates checked on every join.

      Running it safely

      • One click starts every step in order as its own process, with live logs.
      • Resume restarts from the failed step instead of from scratch.
      • A run lock blocks a second run; added after a page reload started a duplicate two-hour production pull.
      • Caches skip the main query if it is under 8 hours old, and the phone and text pulls under 6.
      • Dated backups and test copies before every production change.

      Moving machines

      • The whole pipeline moved from Windows to macOS.
      • Verified against the last Windows run: same 115 columns in the same order, fill rates within 2 points.
      • Hardship predictions identical for 100% of the 230,769 clients in both runs.
      • Paths made OS-neutral; a Windows-only email automation replaced with Power Automate.

      What I'd do next

      1. Refresh the database statistics with an admin: the proper root fix for the slow query, which I could only work around.
      2. Move credentials into a secrets store instead of the scripts.
      3. Run on a schedule, unattended, with alerts when a step fails.
      4. Show the full error in the run screen, not just which step failed.
